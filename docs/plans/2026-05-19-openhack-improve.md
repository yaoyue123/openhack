1 两届赛事背景与演进脉络
2025年11月 · 第一届 —— 依托 XBOW Benchmark 公开靶场（CTF风格），百余支队伍首次公开大规模验证 LLM 自主渗透的可行性。本次比赛赛后的核心痛点：LLM 在复杂靶场中无限循环、事实性幻觉、上下文膨胀。

2026年4月 · 第二届 —— 腾讯自建 Benchmark（在CTF基础上新增 RealWorld 场景：AD域渗透、内网横向、复杂业务逻辑），六百余支队伍在更高复杂度环境下验证技术路线。本次比赛不仅验证了半年来基座模型在自动化渗透领域的进步，也验证了选手们研发的智能体框架在自动化渗透领域能力。本次赛后的核心痛点：在自动化渗透领域中，多智能体框架做了哪些改进，对于基座模型的推理、解决任务能力是正提升？

两届赛事之间，有一条清晰的技术演进脉络。第一届是"百花齐放"的探索期——各队从零开始验证 LLM 能否在CTF基准上完成自动化渗透任务。第二届则是"收敛与深化"——在第一期验证可行后，各队开始系统性解决智能化渗透优化问题。以Harness工程为代表的控制优先 取代 能力优先，成为二期最显著的思想转变。

2 第一届：在XBow Benchmark上寻找答案
XBow Benchmark 带来的核心痛点
第一届赛事依托 XBOW 公开 Benchmark，题目以传统 Web CTF 为主——题型包含XSS、SSTI、SQLI、IDOR、LFI 等。这些题目的特点是：攻击路径相对确定，但需要多步串联（侦察→发现漏洞→构造不同类型 Payload→验证→提交 Flag）。

然而，LLM 在面对这类任务时暴露出三个致命问题：

无限循环：Agent 在同一攻击路径上反复尝试，微调参数命令后再次执行相同工具，无法意识到自己正在"打转"。

事实性幻觉：LLM 生成不存在的工具名称、错误的参数格式，导致执行链断裂；生成错误的Flag并且自信提交等。

上下文膨胀：原始工具输出（如 nmap 扫描结果、HTTP 响应体）直接塞进 LLM 上下文，10-20轮后模型严重降智，忘记最初任务目标。

这些痛点的根源在于：模型能力受限，纯LLM缺乏全局规划及状态抽象能力，对失败信号的无效利用，缺少终止条件与反思机制；缺乏信息压缩机制与结构化的记忆和检索功能，导致模型在工作出现记忆过载导致模型出现目标漂移，注意力涣散的现象；但实践证明，不是模型的能力不够强，而是它需要架构层面的引导、记忆层面的沉淀、控制层面的约束。

3 第二届：腾讯自建Benchmark与Harness
一期遗留问题在二期被放大
第二届赛事采用腾讯自建的 Benchmark，题目复杂度显著提升：

场景更真实：从纯 Web CTF 靶场扩展到 AD 域渗透、内网横向移动、云上云下混合环境

攻击链更长：不再是"发现一个漏洞→提交Flag"的短链，而是类如"Web入口→提权→横向→域控接管"的长链路渗透

业务逻辑更复杂：需要理解业务场景才能发现漏洞（如特定API调用序列才能触发条件竞争）

这些变化使得一期的三个核心痛点非但没有消失，反而因为任务变得复杂而被放大。

二期设计理念的深层共识
Prompt 是引导，代码是边界。架构只提供必要的约束和骨架，不做过度设计。把"必须做"和"绝不能做"写成代码，把"如何做"留给 LLM，模型能力在快速进化，架构越厚重，越容易成为未来的枷锁。结束条件由任务状态决定，而不是由模型当下的主观判断决定。


4 多智能体渗透系统的六维分析框架
本文采用安全学术圈黄老师课题组 Peng et al. (2026) 在 Hackers or Hallucinators? 中提出的 AutoPT 系统化框架以及IEEE/CAA中的接受的Multi-Agent Systems: From Classical Paradigms to Large Foundation Model-Enabled Futures这两篇论文，从六个维度审视 LLM 驱动的自动化渗透系统。该框架回答三个核心问题：

(a) 谁驱动系统？ —— 单Agent独立完成，还是多Agent协作？

(b) 系统如何行动？ —— 高层渗透目标如何分解为可执行攻击路径？规划意图如何转化为实际工具调用？

(c) 系统依赖什么？ —— 长周期任务中历史信息如何维护利用？模型参数化知识之外的外部知识如何按需引入？

围绕这三个问题，框架展开为六个独立且互联的分析维度。以下逐一说明各维度的核心内涵，并结合两届20支队伍的实践进行映射。

4.1
Agent Architecture（智能体架构）
核心问题：谁驱动系统？

一期的架构选择呈现两极分化。Antix 采用纯单Agent架构，通过Meta-Tooling模式将工具调用、规划和反思全部内化于单一LLM，其核心主张是"LLM能力已足够，无需复杂多Agent"。NeuroSploit 则走向另一极端——严格定义了Lead、Recon、Exploit、ReMem四个角色，形成固定的分工流水线。这两种路线在一期的Web CTF场景下各有胜负，并未分出明显高下。

到了二期，面对更复杂的RealWorld场景（AD域、内网横向），十支队伍的架构选择呈现出清晰的收敛趋势：几乎无人坚持纯单Agent或严格的固定角色分工，混合架构成为绝对主流。

这种混合架构有两种典型形态。第一种是"主会话+旁路监督"模式——AI小分队v2的Manager+Solver+Observer三层中，Solver是执行主体，Observer不干预执行流程，仅基于任务目标持续审查执行表现并在适当时机做打断；奇盾明焰的MAIN+Advisor+Alignment+KB Analyst四Agent协作同理，控制面不侵入执行面，而是通过独立的上下文进行纠偏、意图对齐和知识注入。第二种是"薄Planner+轻量Worker"模式——╭(¯v¯)╮的Planner负责全局决策但不执行具体攻击，Executor负责工具调用；星空有云的Tier-0 Dispatcher只做调度不做题，Lead统筹全局不过多干涉Operators的自主执行。

唯一例外是 TCH_Bytex——其黑板系统+蚁群算法的平等Worker动态竞争机制，反对角色分工是"人类局限的投影"，追求涌现式协作。但值得注意的是，即便是这种去中心化架构，其Worker之间仍然通过共享信息素（即外部化的状态存储）实现了隐式的功能分化。

Peng et al. (2026) 的大规模实证为这种收敛提供了量化解释：单Agent在多数Easy和Medium任务上表现不逊色于多Agent，但面对复杂挑战时，多Agent架构通过角色划分实现的上下文分割，能有效降低资源消耗，在长链路渗透中保持更持久的决策质量。二期队伍的集体转向，本质上是对这一规律的工程实践验证。

4.2
Agent Plan（智能体规划）
核心问题：系统如何决策攻击路径？ 

一期在规划维度上已出现明显分化。例如BinX 将攻击计划建模为有向无环图，通过动态图剪枝与路径规划，将自动化渗透任务抽象为图搜索任务。D@WNEDG3 则采用四级步数阈值队列，按步数递进调整任务优先级，本质上是线性管道的一种工程化变体。



二期面对更长链路的 RealWorld 场景，规划维度出现两个方向的深化。第一个方向是“用结构引导推理”——清华颜文字战队╭(¯v¯)╮ 利用树结构维护攻击路径，节点状态随环境反馈动态更新，Planner 基于树的当前快照选取下一任务目标；星空有云则按场景模板（Web/CVE/Net/AD）预定义威胁建模框架，Lead Agent 在模板引导下进行攻击假设生成与优先级排序。第二个方向是“将规划本身变成可编程对象”——For Future 采用纯自然语言 FSM 执行引擎，用“信息充分”等语义判断替代布尔边，让 LLM 同时承担执行者与路由器的双重角色。



Peng et al. (2026) 指出，在多步攻击链中，反馈驱动的自适应重规划是规划维度的关键设计考量——线性管线一旦遇到意外就会卡死，而基于树或FSM的规划能够根据环境反馈动态调整路径。 这恰是三种方案共同的设计内核：清华的树结构依赖任务节点的执行反馈来更新状态、星空有云的场景模板根据Lead的阶段性反馈调整攻击假设、For Future的ralphloop则用eval节点的系统反馈决定是重试还是结束——三者在不同的工程复杂度上，实现了同一种设计理念。该理念的关键是攻击路径规划的可视化与可解释性——Agent 需要知道自己当前在哪、下一步去哪、为什么改变计划。
4.3
Agent Execution（智能体执行）
核心问题：规划意图如何转化为实际操作？

工具是智能体能力范围的边界。因此执行维度关注工具选择与工具调用两个核心环节。执行角色分为集中式执行（单一Agent负责所有工具调用）和专用化执行（不同Agent分别负责侦察、利用、扫描等）。工具选择涉及通用工具、安全专用工具和特种工具的分层。工具调用则涉及接口设计和调用优化。

一期中，yhy 的工具调度是执行维度的极端实践——直接挂载 Kali 容器让 LLM 写 shell 命令，而非通过 MCP 封装限制选择。NeuroSploit 的"驯化工具"概念则代表了另一方向——不只是调用工具，而是深度改造工具使其适配 AI（SKILL.md 规范+MCP 封装）。

这两条路线的本质分歧在于：工具应该原封不动地交给 LLM，还是应该经过适配层"翻译"成 LLM 能稳定执行的形态？

到了二期，一个值得注意的现象是：多数队伍不约而同地选择了 Kali 作为工具底座——星空有云、╭(¯v¯)╮ 等队伍均以 Kali Docker 容器提供统一的渗透工具链。但这并非对 yhy "拥抱真工具"路线的简单回归。二期队伍在继承 Kali 工具链的基础上，普遍在其上叠加了一层"管控层"——不再让 LLM 自由书写 shell 命令，而是通过工程化手段对工具调用进行系统化管控。

Sniper 的 8 层中间件管线是这种管控的系统化创新：上下文摘要→工具降噪→畸形修复→工具检索→任务规划→技能系统→记忆持久化→容错处理，每一层都是执行链路中的必要环节。工具输出的噪声被压缩后再进入上下文，畸形的工具调用被自动修复，不存在的工具由检索层匹配替代方案——这套管线确保了单点工具调用的异常不会传导为整个任务的失败。

ToBeNumberOne 的 统一工具网关则代表了管控的另一种形态：将工具契约抽象为 README.md，Agent 按需读取调用说明，网关统一执行危险命令拦截、资源熔断和路径规范化，实现跨平台的统一分发；戴夫的后花园更进一步，用四道代码关卡（白名单、异常恢复、循环检测、独立顾问）将安全边界全部以代码硬约束实现，拒绝将其寄托于提示词。

一期"拥抱真工具 vs 驯化工具"的路线分歧，在二期已不再是核心争论。二期队伍的共识是：工具可以"真"，但调用必须"管"。 Kali 底座 + 管线/网关/关卡的上层管控，是二期在执行维度上给出的共同答案。

4.4
Agent Memory（智能体记忆）
核心问题：长周期任务中历史信息如何维护与利用？ 记忆管理是论文实证分析中被反复强调的关键维度：在多个 AutoPT 框架中，记忆管理的质量直接决定了 Agent 能否在长链路任务中维持稳定的决策水平。智能体框架中的上下文压缩策略与记忆系统形态的差异，构成了不同框架性能分野的重要解释变量。

两届实践映射： 黑客松一期场景下并未遭遇上下文窗口的硬限额溢出。真正的问题是信息密度过低而非信息总量过大——工具原始输出直接堆积在上下文中，有效的攻击线索被大量噪声稀释。随着轮次增长，模型的注意力不是被限额掐断，而是被噪声逐渐分散，最终表现为意图涣散、目标漂移和重复尝试已失败路径的“打转”行为。换言之，一期不是“记不下”，而是“没记住该记的”——失败边界、已验证的死路、有效 Payload 的构造经验，这些真正有价值的信息未能被结构化地提取和复用。

二期队伍由此形成高度共识：将记忆从模型的“认知负担”变为系统的“外部资产”。 四条典型路径：

AI小分队v2 的 Memory & Idea 双层状态板——Idea 维护攻击方向，Memory 保留事实证据，Observer 持续整理压缩，实现“局部沉淀→全局继承”。

星空有云 的 File-as-Bus——state.json 和 result.json 成为所有 Agent 共享的客观事实来源，所有进展可断点续传。

For Future 的 Markdown 持久化——刻意避免复杂向量检索，认为记忆的准确性比检索的覆盖面更重要。

Sniper 的经验自蒸馏——唯一将记忆从“被动记录”升级为“主动提炼”的方案，攻击成功后自动提取经验并写入知识库，形成自我进化的正向循环。

记忆管理是区分 AutoPT 框架性能的关键因素，上下文压缩的时机与粒度比压缩算法本身更为关键。二期队伍的四条路径，本质上都在回答同一组问题：应该记什么、以什么形式记、在什么时候取出来。

4.5
External Knowledge（外部知识）
核心问题：模型参数化知识之外，如何按需引入领域知识？ 

这是论文实证中最令人意外的发现：外部知识库在多数情况下未能带来正向增益。在对六个含知识库的框架进行的消融实验中，三个在移除知识库后得分显著提高；论文进一步指出，不匹配的检索结果极易误导智能体陷入错误的探索方向。

这一发现直接呼应了 Sniper 在答辩中分享的案例：Agent 面对实际口令为 weaver@2024的 SSH 登录场景，却反复尝试 weaver@2023——其参数化知识仅存在一年的版本偏差，却导致在第三赛区最后两个 flag 上卡了很久。

两届实践映射： 

一期的外部知识利用处于起步阶段。多数队伍依赖模型自身的参数化知识，少数队伍如 NeuroSploit 开始引入经验记忆的自进化机制，但外部知识的形式仍以赛后沉淀为主，尚未实现任务执行过程中的实时检索与注入。

二期队伍面对曾经遇到的 RAG 困境，走出了三种不同的知识利用路径：

路径一：领域知识嵌入而非检索。 队伍“运行完成时”将领域知识内化为“推理空间压缩器”——不直接检索漏洞细节，而是用领域知识减小模型需要探索的攻击方向数量。For Future 则将 Nuclei Templates、SecLists 等以 Markdown 放入 Workspace 环境，让知识成为环境的固有属性而非需要检索的外部资源，从根本上规避了检索误匹配的风险。

路径二：精确匹配与语义检索分层。 颜文字队伍“╭(¯v¯)╮” 基于 30,000+ 条公开 Web 漏洞数据构建知识库，同时支持语义检索与版本精确匹配两种模式——前者应对模糊场景，后者应对 CVE 精确利用场景；星空有云的 CVE 知识库与指纹识别联动：先通过指纹识别确定目标软件及版本，再在 CVE 库中进行精确匹配，避免宽泛检索导致的误匹配。

路径三：独立审核与定向注入。 奇盾明焰的 KB Analyst Agent 为知识注入设置了独立上下文。它读取主会话日志和渗透笔记，通过双知识库 RAG 检索（公开 Writeup 知识库 + 自学习知识库），分析召回结果后，将精炼后的知识内容定向注入主会话。这种“独立审核 + 定向注入”的模式，有效减少了不匹配检索结果直接污染主决策流的风险。

Peng et al. (2026) 的消融实验结论——外部知识库在多数情况下未能带来正向增益——并非否定外部知识的价值，而是揭示了一个更深层的设计原则：知识引入的关键不在于“存了多少”，而在于“在什么时机、以什么精度、经过什么审核机制”进入 Agent 的决策上下文。 二期队伍的三条路径，本质上都是在回答这一组关于时机、精度与审核的设计问题。

4.6
Benchmarks（基准测试）
核心问题：如何公平评估 AutoPT 框架的能力？ 基准测试维度审查现有评估体系的挑战与指标。测试台类型包括：CTF-Based Skill Assessment（CTF靶场）、Single-Host End-to-End（单机渗透）、Multi-Host Multi-Stage Network（多主机多阶段网络）、Stage-Specific Capability Testbeds（专项能力测试）。评估指标涵盖：任务完成率、Pass@k、细粒度进度、Token消耗、时间指标、交互效率、稳定性与一致性、探索与搜索动态、工具调用错误率、Real-World CVE 利用。

两届实践映射： 第一届使用 XBOW Benchmark——公开的 CTF 风格靶场，侧重 Web 漏洞类型（XSS/SSTI/SQLI/LFI/IDOR）。第二届使用腾讯自建 Benchmark——新增 AD 域渗透、内网横向、复杂业务逻辑，更接近 RealWorld 场景。两期的 Benchmark 差异直接塑造了队伍的技术路线：一期侧重短链漏洞利用，二期迫使队伍解决长链路攻击的稳定性问题。这里也很希望师傅们测试完XBow之后，CTF场景测试NYUCTF，评测全题型中智能体的能力；渗透场景和多智能体框架的测评就更希望腾讯的师傅们针对这次赛题中智能体表现不足的地方也出具一个行业内的基准，便于科学评估智能体框架各部分对于自动化渗透任务的提升程度、智能体的盲区、能力边界等问题。


5 三条清晰的架构路线
路线一：极简主义（少即是多）
一期 Antix（#4）→ 二期 Bytex(#3) && For Future（#7），同一团队的技术哲学进化
Antix 在一期的架构极为简洁——单一通用Agent，基于 Claude Code，通过 MCP 只暴露 Python 执行这一接口。200行提示词零调优，无主动扫描SOP，纯AI自主驱动。其核心理念是" Intent Engineering"——从 Prompt Engineering（面向模型）到 Context Engineering（面向Agent）再到 Intent Engineering（面向意图）。

到二期，For Future更进一步，提出 "Less Than Nothing" 哲学：证明纯自然语言驱动的 FSM 执行引擎已足够强大。他们的控制实验极具说服力——Day 1 纯 Claude Code 排名第 42（这约等于Claude Code的消融实验，如果排名比这个高，说明框架做的是正优化），Day 2 完整系统上线后峰值冲到第 4，最终排名第 7。同模型、同战队，唯一变量就是工程化。

核心理念
零领域知识不是遗漏，是主动排除。要做的是 Pattern（宏观行为）+ Workspace（环境）+ Intent（意图），而非编码专家SOP。LLM 的指令遵循能力已足够强，硬约束反而会损害推理空间。Less Is More——工程化应尽可能少，让 LLM 的推理空间尽可能大。

路线二：控制优先（Control First）
一期 AI小分队（#7）→ 二期 AI小分队v2（#1）；奇盾明焰（#6）；戴夫的后花园（#10）
这条路线认为 LLM 的能力已经足够强，真正的问题是让它不跑偏。AI 小分队从一期"蜂群架构+三大纠偏"（防降智/防沉迷/防依赖）进化到二期"Manager+Solver+Observer 三层解耦+RTK Rewrite"，核心始终围绕"稳定骨架而非能力枷锁"。

RTK Rewrite 是全场对"上下文腐败"问题思考最深入的工程解——原始工具输出不能直接塞进上下文，需要经过 Rewrite → Compaction → Solver Context 三层处理。Observer Agent 持续审查最近几轮执行表现，生成修正建议，维护双层状态板。Ralph-Loop 将"任务是否结束"的判断从模型主观决策中抽离，交给系统状态约束——结束条件由任务状态决定，而非模型当下的主观判断。

奇盾明焰的 Harness 设计 从另一角度解决同一问题——控制面与执行面分离，MAIN 主会话+纠偏+意图对齐+知识注入的四 Agent 协作设计，有效解决意图涣散、自评估盲区和上下文饱和三大困境；戴夫的后花园的四道关卡代码硬约束则提出最极端的安全哲学——"不相信大模型的自制力"，用代码约束 > 提示词约束。

核心理念
Prompt 是引导，代码是边界。把"必须做"和"绝不能做"的硬约束写成代码，把"如何做"留给 LLM。旁路观察（Observer/Harness）比直接接管更优雅——工程师只评估不干预，智能体保持自主。

路线三：涌现与自组织（去中心化）
代表：TCH_Bytex（#3 AK）
涙笑师傅是单人参赛表现最好的选手，设计很有深度——Bytex的设计是黑板系统+蚁群算法+涌现行为的去中心化多Agent架构，其核心主张具有强烈的颠覆性：明确反对固定角色分工，认为这是“人类认知局限的投影”。

平等的 Worker 通过黑板共享记忆，通过蚁群信息素机制自然形成协作秩序，无需自上而下的调度器：成功推进时增加信息素浓度吸引其他 Worker，失败时递减浓度自然抑制无效方向，任务分配从 Worker 的自主行为中涌现而出。

最终成绩证明了这一理念：全场唯一 AK，7,692 元成本。这揭示了一个设计层面的可能性——当攻击路径高度不确定时，固定分工可能过早锁定次优策略，涌现式协作反而具备更高的探索弹性。

核心理念
Agent 应自组织涌现，而非硬编码角色。角色分工不是 AI 的最优解，而是人类认知局限的投影。黑板系统让信息自然流动，蚁群信息素让协作自然形成。涌现行为使系统在不确定攻击面上保持探索弹性，避免固定分工的过早锁定。


6 共识与痛点
四个共识
1
不要相信大模型的自制力，小心幻觉
Prompt是引导，代码是边界。 把“必须做”和“绝不能做”写成代码，把“如何做”留给LLM。

2
记忆属于系统，不属于模型
系统负责“记什么、何时取”，模型只负责基于当前上下文推理。记忆的质量远比记忆的体量更重要。
3
拥抱真工具，警惕 MCP 膨胀
给LLM一个真实shell环境，可能比给它30个MCP工具更强——集成工具能力，但需要对工具做约束。

4
循环检测是核心痛点，需要系统级方案解决
模型自身缺乏从海量搜索空间中自主跳出失败路径的能力，需要系统级方案对模型的行为进行纠偏


三个痛点
1
上下文腐败（Context Corruption）
原始工具输出直接塞进 LLM 上下文会导致模型快速降智。RTK Rewrite、8层管线、笔记Agent等创新都是对这一问题的工程解，但还没有银弹方案。这是限制Agent完成长链路攻击（Web→提权→横向→域控）的核心瓶颈。Peng et al. 的大规模实证也证实：单Agent面对复杂挑战时每轮Token消耗显著高于多Agent框架，根源就在于上下文膨胀。

2
外部知识工程薄弱
AI 小分队两届都在没有依赖外部知识，说明当前阶段工程架构的重要性大于知识工程。但随着题目复杂度提升，没有知识库/RAG/漏洞库的队伍将面临天花板。Peng et al. 的实证发现与这一观察一致：外部知识库在大多数情况下未能带来正向收益，不匹配的检索结果反而容易误导 Agent。如何让知识在“正确的时机、以正确的精度”进入决策上下文，仍是全行业待解难题。

3
成本与效果的平衡
AI 小分队 v2 的总成本约 7,385 元，是第一届（1,057 元）的 7 倍。7 模型并行竞争策略带来效果的同时大幅推高成本。TCH_Bytex 以 7,692 元成本实现全场唯一 AK，说明成本与效果之间并非简单线性关系——关键在于花对钱，而非花少钱。Peng et al. 将 Token Usage 作为核心评估指标之一，但如何在有限预算下最大化 Pass@k 尚无系统性答案。


7 写在最后
两届黑客松 20 支队伍的技术演进，清晰地勾勒出 AI 自主渗透测试领域从探索期走向工程收敛期的轨迹。

第一届是百花齐放——在 XBOW Benchmark 上，各队从零开始验证 LLM 能否完成端到端渗透。Antix 用200行提示词证明极简可行，NeuroSploit 用4角色分工证明复杂协作也可行，AI小分队 用蜂群架构证明成本可控也可行。但所有队伍都遇到了相同的问题，比赛时间内没有队伍AK赛题。

第二届是收敛与深化——在腾讯云鼎实验室自建 Benchmark 的 RealWorld 场景下，上下文污染被确认为长链路攻击的核心瓶颈，多模型并行竞争成为头部队伍的标配策略，Harness工程被采纳为保障稳定性的关键设计。二期工程重心从“让模型更强”转向“让模型不跑偏”。

两期比赛中，优秀队伍的探索都指向一个朴素判断：在当前模型能力下，Harness 工程是让 Agent 稳定执行长链路攻击的前提。Prompt 引导方向，代码守住边界——工程负责“不跑偏”，模型负责“如何做”。

但值得仔细思考的是：上下文污染、幻觉、循环问题，本质上是 LLM 在长程任务中的通用缺陷，并非渗透测试独有。Harness 工程缓解了LLM在自动化渗透领域的缺陷，但并未根除病因。这些问题是交给专门研究LLM的工程师解决？还是交给渗透工程师解决？

真正属于自动化渗透测试的结构性难题，藏在这两次比赛共识的边界之外。在对抗性、部分可观测、反馈时延不确定的环境中，如何设计一个既能保持探索广度又能维持决策精度的闭环系统？对于自动化渗透任务来说，攻击面是开放的，Agent 必须首先回答“这里有漏洞吗”，而这个问题可能本身没有答案——终止条件因此成为开放问题。工具输出无法直接验证是否漏洞存在，nmap 被防火墙吞掉的结果和真的没有端口开放，Agent 可能无法区分。漏洞渗透的最优路径未必是符合预期的，过度编码专家经验反而可能将其排除。自动渗透领域的模型和框架不仅需要解决“漏洞在这里，怎么走是对的？”，还需要解决“如何准确完成任务而不跑偏？”，可能还包括“哪里有漏洞？哪个漏洞是真实存在的？攻防怎么又快又准又好？”，两次赛题都是有详细的提示信息，并且处于确定解的环境下，那么真实环境的业务系统，不知道漏洞在哪，没有提示，模型怎么成功利用漏洞，怎么通过安全护栏保障渗透能力和范围，还是待解决的问题。

第一届黑客松验证了模型+框架的漏洞利用能力，给出了“漏洞在这里，怎么走是对的”的许多解；第二届验证了模型利用复杂漏洞是否具有稳定性的问题，在“如何让模型准确完成任务而不跑偏”上给出了答案；那第三届需要解决的，或许正是这些渗透测试独有的、无法被通用 Agent 方法论消解的问题。
